# `piitag` — Python port of Desert Ant Labs' Redact SDK

**Implementation plan for a coding agent.** Source of truth for behavior is the
Swift reference implementation at
[`Desert-Ant-Labs/desert-ant-core`](https://github.com/Desert-Ant-Labs/desert-ant-core/tree/main),
specifically `Sources/Redact/*.swift` at tag/revision matching model revision
`v0.4.0` / SDK version `3.2.0`. Do not guess at behavior — port the Swift
line-for-line where this plan says "port," and validate every stage against
the oracle fixtures in `Tests/RedactTests/Resources/`. Where no fixture
exists (noted per-phase below), flag it back rather than inventing expected
output.

Model weights and taxonomy come from the Hugging Face repo
`desert-ant-labs/redact`, pinned at revision `v0.4.0`. **License note:** the
weights are under the Desert Ant Labs Source-Available License (free under a
MAU threshold, commercial license required at scale) — this applies to the
weights, not to `piitag`'s wrapper code. Same pattern as `taxotag`: a
`NOTICE.md` pointing at the license, no weights bundled in the sdist/wheel.

**This is a bigger port than `taxotag`.** Redact is not a static-embedding
classifier — it's a windowed BERT-style token classifier (BIOES tagging),
layered with a large deterministic regex/checksum recognizer set (~20
countries' national ID formats, IBAN/BIC, card Luhn, phone heuristics) and a
non-trivial span post-processing pipeline (hysteresis, name-particle
bridging, address recognizers, hybrid deterministic/neural resolution).
Treat the phase count below as intentional — each phase should be its own
PR, independently testable, rather than one large sweep.

---

## 0. Goal and non-goals

**Goal:** a pure-Python (+ numpy + a TFLite runtime + `regex`) package that
reproduces `Redact.redaction(of:)` / `Redact.detect()` from the Swift/Kotlin/JS
SDKs — deterministic recognizers, windowed neural NER, and the hybrid merge —
to parity with the committed oracle corpus, installable via `pip install piitag`.

**Non-goals for v1:**
- No training code, no fine-tuning, no `parity_gen.py` equivalent (that's
  the upstream training repo's tool, not something this port reproduces).
- No Core ML backend — LiteRT/TFLite only, same reasoning as `taxotag`.
- No streaming/incremental API — `redaction()` takes a full string, matching
  the Swift/JS/Kotlin surface.
- `IMEI` deterministic-only label is in scope (it's cheap — just a regex +
  Luhn check already covered by Phase 4); no neural IMEI detection exists
  upstream either.

## 2. Dependencies

Runtime:
- `numpy`
- `huggingface_hub` — download + cache assets from `desert-ant-labs/redact`
- `regex` (the PyPI package, import name `regex`, **not** stdlib `re`) —
  required because the Swift patterns use Unicode property escapes
  (`\p{L}`, `\p{N}`) that stdlib `re` has never supported, plus the
  Deterministic.swift dispatch relies on Unicode-aware `\b` and
  case-insensitive matching behaving the same way ICU/Swift's regex engine
  does. **Do not attempt this port with stdlib `re`** — it will silently
  diverge on any non-ASCII input, which is the whole point of a 27-language
  PII detector.
- No `model2vec` this time — redact has no static-embedding stream, it's a
  straight token classifier. One fewer dependency than `taxotag`.
- Same TFLite runtime story as `taxotag`: `ai-edge-litert` primary,
  `tensorflow` fallback extra.

Dev/test: same as `taxotag` — `pytest`, `pytest-cov`, `ruff`, `mypy`,
`build`, `twine`, `python-semantic-release`.

## 4. Phase 2 — UTF-16 offset helper (`_utf16.py`) — build this before anything else

**Why this phase exists and comes first:** every span, every regex match
offset, every oracle fixture coordinate in this system is a **UTF-16 code
unit offset**, not a Python string index. Python `str` is indexed by Unicode
code point. For BMP-only text (the overwhelming majority of PII: names,
emails, numbers) the two coincide and you'll never notice a bug. The moment
an astral character appears before or inside a match — an emoji, some rare
CJK extension characters — code-point indices and UTF-16 indices diverge,
and every downstream span will be off by one for the rest of the string.
This is exactly what the Swift test suite's `😀 call +34 600 100 200...`
case is designed to catch, and your Python port needs the same trap wired
into its own test suite from day one, not discovered later.

Port `Span.swift`'s `UTF16Text` as a Python class:

```python
class UTF16Text:
    """UTF-16 code-unit-indexed view over a str, matching the Swift/JS
    reference pipeline's offset convention exactly."""
    def __init__(self, text: str) -> None:
        self.string = text
        self._units: list[int] = ...  # via text.encode("utf-16-le"), 2 bytes per unit

    def __len__(self) -> int: ...
    def scalar_at(self, i: int) -> str | None: ...   # single-unit decode; BMP assumption, matches Swift
    def slice(self, a: int, b: int) -> str: ...        # decode units[a:b] back to str
    def find(self, needle: str, start: int) -> tuple[int, int] | None: ...
    def is_whitespace_at(self, i: int) -> bool: ...
    def is_word_char_at(self, i: int) -> bool: ...      # alphabetic OR numeric-type OR the specific
                                                          # combining-mark categories Swift lists —
                                                          # port the exact category set, don't
                                                          # approximate with `str.isalnum()`
```

Implementation notes:
- Build `_units` via `list(struct.unpack(f"<{len(text)*2//2}H", text.encode("utf-16-le")))`
  or simpler: `array.array("H")` from the UTF-16LE bytes. Surrogate pairs
  become two entries, exactly matching Swift's `Array(string.utf16)`.
- `scalar_at` only needs to handle a single code unit (BMP) — same
  assumption the Swift comment states explicitly ("surrogate pairs read as
  their leading unit — PII text is effectively all BMP"), so don't
  over-engineer surrogate-pair reassembly here; the point of this class is
  matching the reference's *offsets*, not full Unicode correctness at every
  method.
- `is_word_char_at`: port the exact category list from `Span.swift` —
  alphabetic, any Unicode `numericType`, plus `Nd`/`Nl`/`No`/`Mn`/`Mc`/`Me`
  general categories. Use `unicodedata.category(ch)` for the general
  category and a small manual check (or the `regex` module's Unicode
  property support, e.g. `regex.match(r'\p{Alphabetic}', ch)`) for the
  alphabetic/numeric-type parts, since stdlib `unicodedata` doesn't expose
  "is alphabetic" or "numeric type" directly the way Swift's
  `Unicode.Scalar.Properties` does.

**Test (write this now, not later):** a handful of hand-built cases
including the exact `😀 call +34 600 100 200...` string from
`HybridRedactionTests.swift`, asserting `slice()`, `find()`, and computed
offsets match the Swift test's committed expectations (`item.range` values
in that file). This becomes `tests/reference/utf16_cases.json` if you want
it fixture-driven rather than inline asserts — either is fine, but don't
skip building this test before Phase 4 and 5 start relying on the class.

## 5. Phase 3 — Tokenizer (`_tokenizer.py`)

Structurally the same algorithm as `taxotag`'s Gist tokenizer (XLM-R
SentencePiece Unigram, Viterbi decode) — **reuse that implementation as your
starting point** rather than writing from scratch — but with two concrete
differences to port carefully:

1. **Different binary container.** Magic bytes are `RDTK` (Redact), not
   `GSTK`. Header layout otherwise matches Gist's format (`unk_id`, `bos_id`,
   `eos_id`, `count` as little-endian int32, then `count` float32 scores,
   `count` uint16 piece lengths, then the piece bytes back-to-back) — but
   confirm this field-for-field against `Tokenizer.swift`'s `init?(bytes:)`
   rather than assuming it's identical to `taxotag`'s reader; get the exact
   byte offsets right.
2. **Simpler normalization — no tilde special-case, no control-char
   stripping.** Redact's `tokenize(_:)` does: NFKC normalize (plain
   `unicodedata.normalize("NFKC", s)`, no fullwidth-tilde workaround) → trim
   and collapse whitespace runs to single spaces (the loop in
   `Tokenizer.swift` lines ~104-116, port directly — it's simpler than
   Gist's `nmtNormalize`) → prefix with `▁` (U+2581) and replace remaining
   spaces with `▁` → Viterbi segment. Don't carry over Gist's control-character
   stripping table — it isn't present in this file, and porting it in by
   habit would be a real behavioral bug, not a harmless no-op.
3. **Vocab lookup:** the Swift `VocabIndex` uses byte-keyed open addressing
   specifically to dodge a Swift `String`-hashing bug (canonical-equivalence
   collisions). That bug doesn't exist in Python — a `dict[bytes, int]`
   keyed on UTF-8-encoded piece bytes is both correct and fast; you don't
   need the open-addressing scheme, just don't accidentally key on `str`
   pieces that have gone through any Unicode normalization that could
   collapse two distinct byte sequences. Keying directly on the raw UTF-8
   `bytes` sidesteps the whole class of bug the Swift comment describes.

**No committed tokenizer oracle exists for Redact** (unlike Gist's
`gist-sdk-oracle.json`). Options, in order of preference:
1. Run a handful of representative multilingual strings (reuse a few rows
   from `deterministic_corpus.json`'s `text` field, and the emoji test
   string) through the actual JS or Swift SDK (`npm i @desert-ant-labs/redact`
   in a scratch project) and record the token ids as
   `tests/reference/tokenizer_cases.json`. This is real ground truth — do
   this rather than skipping it.
2. If that's not feasible in your environment, fall back to structural
   tests only (round-trip determinism, correct handling of the emoji case's
   offsets via Phase 2, vocab lookup correctness on known pieces) and
   **say explicitly** in the PR description that tokenizer-id parity is
   unverified against the reference SDK, so a human can decide whether to
   close that gap before v1 ships.

## 7. Phase 4b — Deterministic regex patterns and dispatch (`_deterministic.py`, part 2)

Port the pattern definitions ("MARK: patterns" and "MARK: context patterns"
sections) and the `detect(_:enabled:)` dispatch function, using the `regex`
package with the `regex.IGNORECASE` and Unicode-property syntax (`\p{L}`,
`\p{N}`) as written in the Swift source — these translate close to
verbatim into `regex` module syntax, unlike stdlib `re`.

Structure:
```python
OWNED: frozenset[str] = frozenset({
    "EMAIL", "URL", "IP_ADDRESS", "CREDIT_CARD", "SSN",
    "BANK_ACCOUNT", "ROUTING_NUMBER", "TAX_ID", "GOVERNMENT_ID", "PASSPORT",
    "DRIVERS_LICENSE", "IMEI",
})

def detect(text: str, enabled: frozenset[str] | None = None) -> list[Span]: ...
```

Port the full `detect()` body's dispatch order from `Deterministic.swift`
lines ~255-309 **in the same order** — order matters here because later
recognizers' context windows (`has_context`, `before`) look at text that
earlier recognizers may or may not have already claimed, and the final
`merge()` step's tie-breaking (`length desc, then score desc`) depends on
what got added and in what sequence. Port `merge()` itself directly too
(lines 312-324) — it's the same sort-then-greedy-overlap-resolution shape
used again in `Pipeline.swift`, so getting it right once here pays off in
Phase 5.

Key things **not** to simplify or "clean up" during the port, because each
is there for a specific correctness reason documented in the Swift comments:
- `ibanTrim` — cuts an IBAN candidate to its country's exact length because
  the regex is deliberately loose (to allow grouped IBANs with spaces) and
  would otherwise swallow a following word.
- The `keywordValue` two-step (keyword match, then a separate value regex
  applied to the text *after* the keyword) for driver's license and
  national ID document numbers.
- `trimWord` — un-swallows a trailing lowercase word that a greedy keyword
  value match absorbed.
- The credit-card recognizer's `Set(dg).count <= 1` guard (rejects
  `0000 0000 0000 0000`-style non-cards that would otherwise Luhn-pass only
  by coincidence — actually check: this guards against degenerate repeated-digit
  strings, port the exact condition, don't assume you know why and rewrite it).

**Test — hard gate:** run every one of the 1,362 rows in
`deterministic_corpus.json` through `detect(text)` (with `enabled=None`,
i.e. `OWNED`) and assert the returned spans exactly match the `py` field
(same start, end, label triples, same count, order-insensitive is fine but
note the corpus rows are presumably already in a canonical order — check
whether your `detect()` needs its own sort to line up, and if the merge
step doesn't guarantee a specific order, sort both sides identically before
comparing). **100% pass on this fixture is the phase's exit criterion**, not
"most pass" — every deviation here is either a transcription bug in your
port or a genuine discovery worth flagging, not something to average away.

## 9. Phase 5b — Name/address heuristics and final cleanup (`_pipeline.py`, part 2)

The higher-level, more heuristic pieces — port each function directly from
`Pipeline.swift`:

- `is_shouting`, `title_case`, `model_input` (ALL-CAPS title-casing before
  the model sees text — **note the guard**: only applied when the
  title-cased string has the *same UTF-16 length* as the original, because
  some casing changes aren't 1:1, e.g. German `ß`→`SS`, and applying it
  anyway would shift every span; port `titleCase`'s `nil`-on-mismatch
  behavior faithfully as a `None` return in Python).
- `casing_is_informative` — gates whether capitalization can be trusted as a
  name-boundary signal.
- Address recognizers: `attach_building_numbers`, `redact_us_street`,
  `attach_state_codes`, `redact_secondary_address` — each ports one
  regex + a "don't overlap what's already claimed" occupancy check
  (`free(a, b)` / the `occ` list pattern) directly from the Swift.
- `relabel_by_context` — the two hand-tuned context sniffs (`PHONE` near an
  account-number keyword → relabel as `BANK_ACCOUNT`; `GOVERNMENT_ID` near
  driver's-license keywords in several languages → relabel as
  `DRIVERS_LICENSE`). Port the literal keyword substring list, including
  the German `ü`/`u` variant handling (`"führerschein"` / `"fuhrerschein"`).
- `clean_spans` — trailing/leading punctuation trim, plus the name-specific
  logic that strips honorific titles (`Mr`, `Dr`, `Señor`, etc. — the
  `stripTitles` set) from the front of a `GIVEN_NAME`/`SURNAME` span and
  drops the span entirely if nothing but a title is left.
- `gap_is_name_like`, `bridge_name_gaps`, `extend_particle_names` — the
  "Jean **de** la Cruz" / "**van der** Berg" name-particle handling. Port
  the two particle sets (`particles` vs `all_particles` — they're
  deliberately different, don't merge them) and the gap-tolerance rules
  (max 20 UTF-16 units, no punctuation from `bad_gap_re`, every non-particle
  token in the gap must be a single letter or already capitalized).
- `hysteresis(t, scored, high)` — the low-confidence name-span rescue: a
  weak-scoring name span gets kept if it's adjacent (touching, or separated
  by a name-like gap) to an already-kept name span. Port the fixed-point
  loop exactly (it repeats until no more weak spans get pulled in).
- `resolve(det_spans, ml_spans)` — the hybrid merge. Port precisely: an ML
  span overlapping a det span of the **same** label suppresses the det span
  (neural refines/replaces deterministic — this is how the PHONE
  refinement in `HybridRedactionTests.swift` works); an ML span overlapping
  a det span of a **different** label is dropped entirely (deterministic
  wins on label conflicts); non-overlapping ML spans always survive. Then
  `merge_same_label` on the combined, unsuppressed set.
- `mask_text(text, spans)` — replaces `Deterministic.owned`-labeled spans
  with spaces (preserving `\n`) before the masked text goes to the neural
  model, operating over the UTF-16 unit array from Phase 2, not over the
  Python `str` directly.

**Test:** extend `tests/reference/pipeline_cases.json`, and specifically
add the exact scenarios from `HybridRedactionTests.swift` (phone-only
option filtering keeps structured matches out of neural input; structured +
phone redactions keep original ranges; neural phone match replaces the
overlapping deterministic match) as integration-style tests once Phase 6
and 7 exist — flag them here so they aren't forgotten, even though they'll
actually run against Phase 7's `Redact` class.

## 10. Phase 6 — Neural head and windowing (`_head.py` + windowing in `model.py`)

### 6a. Head wrapper
Same shape as `taxotag`'s TFLite wrapper, adjusted for redact's fixed tensor
contract:
```python
class Head:
    def __init__(self, tflite_path: str | Path) -> None: ...
    def run(self, input_ids: np.ndarray, attention_mask: np.ndarray) -> np.ndarray:
        # both shape (1, 256) int32; returns logits shape (1, 256, num_labels) float32
        ...
```
Both the Core ML and LiteRT exports take a **fixed 256-length int32 window**
with baked position ids (`0..256`) and token type ids (`0`, since there's
only one segment) — per `Model.swift`'s comment, the `.tflite` graph only
declares `input_ids` and `attention_mask` as real inputs and bakes the rest,
but building all four tensors and passing them (letting the session ignore
the extra two) matches what the Swift/JS code does and costs nothing. Verify
the actual tensor names via `interpreter.get_input_details()` rather than
hardcoding `"input_ids"`/`"attention_mask"` blind.

### 6b. Windowing (`ml_spans` in `Model.swift`, ~lines 55-95)
This is the trickiest piece of glue in the whole port — port it carefully,
function by function:
1. Tokenize the (deterministic-masked) input text; get per-token UTF-16
   offset spans by scanning each token's surface (minus the `▁` metaspace
   marker) forward from a cursor through the source text —
   `reconstructOffsets` in `Model.swift`, lines 128-145. Port this exactly;
   it's a linear scan using `UTF16Text.find`.
2. Slide a window of `max_content = 254` tokens (`seq=256` minus 2 for
   `<s>`/`</s>`) across the token sequence with `stride=64` overlap
   (`step = max_content - stride = 190`), running the head on each window.
3. Per window: prepend `bos_id`, append `eos_id`, run the head, softmax the
   logits per position, take the argmax label and its probability.
4. Convert each window's per-token BIOES tags to spans via
   `bioes_to_spans` (Phase 5a), but first zero out any tag whose probability
   is below `min(low_score=0.3, min_score)` (the `usableTags` line) — this
   is a **window-local** low bar, separate from the final `min_score` gate
   applied later via hysteresis.
5. **Deduplicate across overlapping windows**: keep one span per
   `(start, end, label)` key at its best observed score across all windows
   that produced it (the `best`/`scored` dict-and-list pattern in
   `Model.swift`) — a span near a window boundary is re-emitted by both the
   window that starts before it and the one that starts after, and you want
   the max-confidence version, not duplicates.
6. After the window loop: `hysteresis` → `merge_priority` → the chain of
   address recognizers (`attach_building_numbers`, `extend_particle_names`,
   `bridge_name_gaps`, `snap_spans` — note the Swift composes these as
   nested calls, get the **exact order** right, it's
   `attachBuildingNumbers(extendParticleNames(bridgeNameGaps(snapSpans(...))))`)
   → `redact_secondary_address`, `attach_state_codes`, `redact_us_street`
   (again, exact nesting order from `Model.swift` line 93) → a final
   `merge_priority`.

**Test:** no dedicated upstream fixture for this phase either — this is
genuinely the hardest thing to validate without running the reference SDK
side-by-side. At minimum: construct synthetic `Head` doubles (a fake
interpreter returning hand-specified logits) mirroring the Swift test
suite's `NoEntitiesSession`/`PhoneSession` test doubles in
`HybridRedactionTests.swift`, and reproduce those exact test cases in
Python — you have the expected outputs (`redactedText`, `items`,
`confidence` values) written out in that file already, translate them
directly into Python fixtures rather than re-deriving them.

## 11. Phase 7 — Public API (`model.py`)

Mirror the Swift/JS public surface:

```python
@dataclass(frozen=True)
class Item:
    label: Label
    original: str
    placeholder: str
    confidence: float
    start: int            # UTF-16 offset into the original text
    end: int               # UTF-16 offset into the original text

@dataclass(frozen=True)
class Redaction:
    redacted_text: str
    items: list[Item]
    def restore(self, processed: str) -> str: ...

@dataclass
class Options:
    minimum_confidence: float = 0.6   # clamped to [0, 1], NaN/inf -> 0.6
    labels: frozenset[Label] | None = None   # None -> Label.default_enabled (all but ORG)

class Redact:
    def __init__(self, *, directory: str | Path | None = None) -> None: ...
    def redaction(self, text: str, options: Options | None = None) -> Redaction: ...
```

Port `Redact.redaction(of:options:)` from `Redact.swift` (lines 158-189)
directly: compute spans via the deterministic layer with `PHONE` explicitly
allowed through (even when the caller didn't request it, it needs to be
visible so neural inference can refine it — see Phase 5b's `resolve` note),
mask only the `Deterministic.owned` subset before neural inference, combine
via `resolve` + `clean_spans` + `relabel_by_context`, filter by the
caller's `Options.labels` and `minimum_confidence`, sort by
`(start, then end)`, then walk the text building the redacted output and
numbered placeholders (`[LABEL_1]`, `[LABEL_2]`, ...) **per label**, exactly
as `Redact.swift`'s `redaction(of:)` loop does (lines 158-182) — including
its overlap guard (`s >= last, s < e, e <= units.count`), which silently
drops any span that would overlap a previous one or fall outside the text,
rather than raising.

`restore()` is a straightforward sequential placeholder substitution —
`Redaction.swift` lines 37-41 — note the doc comment's reasoning for why
numbered, bracket-delimited placeholders make this safe and
order-independent (no placeholder is ever a prefix of another).

## 16. Suggested execution order for the agent

1. **Phase 1** (pull reference + corpus + assets) — nothing else can start
   without this.
2. **Phase 2** (UTF-16 helper) — everything downstream depends on getting
   this right; build its test (including the emoji case) before moving on.
3. **Phase 3** (tokenizer) — adapt from `taxotag`'s implementation, don't
   restart from scratch.
4. **Phase 4a → 4b** (deterministic checksums, then patterns + dispatch) —
   4a is quick, low-risk, and de-risks 4b. 4b's corpus test is your first
   real hard gate.
5. **Phase 5a → 5b** (span algebra, then name/address heuristics) — 5a is
   small and mechanical; 5b is the largest single chunk of heuristic logic
   in the port, budget the most review time here.
6. **Phase 6** (head + windowing) — depends on 2, 3, 5a, 5b all being solid.
7. **Phase 7** (public `Redact` API) — the integration point; this is where
   the `HybridRedactionTests.swift` scenarios finally become end-to-end
   tests.
8. **Phase 8** (asset loading) — can actually be done in parallel with 3-7,
   it has no dependency on the rest.
9. **Phase 14** (CI) as you go, not bolted on at the end — the corpus gate
   from 4b should be wired into CI as soon as 4b lands.
10. **Phase 9** (CLI/polish) and **Phase 15** (packaging) last.

Flag back to the user (don't silently guess or loosen a tolerance) if:
- The `RDTK` binary format's header layout doesn't match Gist's format
  field-for-field once you inspect the actual downloaded
  `redact_tokenizer.bin` bytes.
- `labels.json`'s id→label set uses a BIOES tag shape you didn't expect
  (e.g. missing an `S-` prefix for some label, or unexpected label names).
- You can't get real reference-SDK token ids for Phase 3's oracle (no
  Node/Swift toolchain available) — say so explicitly rather than shipping
  an unverified tokenizer.
- Any row of `deterministic_corpus.json` fails after a careful, direct port
  of the matching Swift logic — that's a real bug to fix, not noise to
  average over.
- The synthetic-session test doubles from `HybridRedactionTests.swift`
  don't reproduce the exact `redactedText`/`items`/`confidence` values
  committed in that file once ported — same standard as the corpus: exact
  match or a flagged discrepancy, not "close enough."
